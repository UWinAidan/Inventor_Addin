# 160: Spike: Inventor's hole table or a custom table; reading a view's holes and its ordinate origin

- **Milestone:** M4 part 2
- **Feature spec:** `docs/features/04-hole-table-wizard.md` ("Design decision to settle with a spike on Windows", "Add-in side", "Decided behaviour", open questions 15 to 17)
- **Status:** done (rounds 1 to 7, 2026-11-12 to 2026-11-17; Aidan passed round 7 on 2026-11-17)
- **Depends on:** none (independent of the Core tasks 155 to 159)
- **Needs:** **windows** (spike, local session with Aidan in Inventor 2026)
- **Parallel-safe with:** 155 to 159 (separate spike branch)

## Goal

Settle how the add-in side of the wizard talks to Inventor before any add-in task is written: which table it draws (Inventor's own hole table or a custom table with our own tags), how it finds a view's holes and their sheet positions, how it reads the view's ordinate-dimension origin (Aidan, 2026-11-12: the wizard uses it and never invents one), and where the wizard keeps its edits so Update and the Edit Table tab can re-open a table. Nothing from this spike is merged.

## Questions

**A. Which table.** Aidan's two tables share one tag sequence (precision letters first), have custom titles (`Precision Table: <view>`, `Tap and Clearance Table: <view>`), the columns HOLE, XDIM, YDIM, DESCRIPTION, NOTES, a DESCRIPTION cell merged across each group's rows with stacked deviations, NOTES text per group, and Split groups.

1. **Inventor's hole table** (`Sheet.HoleTables`; `HoleTables.Add` from a view and an origin?): can it take
   - our tags (`HoleTableRow.HoleTag` writable?) and a letter sequence that runs on from one table to the other?
   - a custom title, our five columns, our description text (a row's description cell writable, or overridden?)
   - merged description cells or one description per group?
   - only the holes we choose (filtering rows, or two tables with complementary row sets)?
   - and does it keep our overrides when the model changes and Inventor updates it?
   - Does it use the view's ordinate origin, or its own origin indicator?
2. **A custom table** (`Sheet.CustomTables.Add`?): titles, column widths, row heights; merged cells (is there an API to merge, or only by hand?); stacked text or two lines in one cell (formatted text in a cell?); Inventor's counterbore, countersink and depth symbols in a cell (question 15).
3. **Tags on the view** with a custom table: what keeps a tag next to its hole when the view moves or the model changes (a leader note or general note attached to the hole's circle by a `GeometryIntent`? a balloon? a sketched symbol?). Does it follow, and does it disappear or orphan when the hole is deleted?
4. **Precision centre marks** (the reference's filled-quadrant marks): a centre mark style, a sketched symbol, or nothing for the first version?

**B. Reading the view.**

5. **The holes in a view and their sheet positions:** from the view's drawing curves (`DrawingView.DrawingCurves`, a curve's `ModelGeometry` back to the `HoleFeature`, `CenterPoint` on the sheet?), or from the model's hole centres through `DrawingView.ModelToSheetTransform`? Which one tells which centre index of the feature an instance is (task 155's `Id`), and which one tells a hole seen end on from one seen from the side (question 16)?
6. **Hidden holes:** a hole behind another face, a hole in a section or break-out, a suppressed instance, a pattern of holes (a `RectangularPatternFeature` of a hole: does each occurrence come back as the same `HoleFeature`?). Which should be listed? Ask Aidan as they come up.
7. **Holes in an assembly view**: a view of an assembly reaches holes through occurrence proxies. Is that wanted in the first version, or part views only? Ask Aidan.
8. **The ordinate origin:** where an ordinate dimension set or a single ordinate dimension keeps its origin (`OrdinateDimensionSet` and its origin member?, `OrdinateDimension.Origin`?), how to tell which view a dimension belongs to, and the origin's sheet position. What happens with ordinates made by Inventor's "Ordinate Dimension Set" and by the single "Ordinate" command; several sets on one view (question 17).
9. **The title block corner** for Align: the title block's position and size on the sheet (`TitleBlock.Position`?, `RangeBox`?), and the border's inner edge.

**C. Keeping the wizard's edits.**

10. Where the swaps, deletes, splits and notes (task 158's `HoleTableEdits`) live so Update and the Edit Table tab can rebuild the plan: attributes on the table, on the sheet, or on the drawing (`AttributeSets`, as AWB Hole stores hole data). Do they survive Save, close and reopen, and copying the drawing?
11. A hole instance's `Id` across model changes: does a feature name plus centre index stay steady when a sketch point is added or deleted, or is the sketch point's own identity (reference key?) better?

## How

- A spike branch `spike/160-hole-table`, off `main`, with a temporary developer button. Aidan makes a test part of his own (no employer data) with each hole type in scope (spec 04 question 8), a drawing with a base view, ordinate dimensions from a corner, and a second view with no ordinates.
- Round 1 (B first, since both table routes need it): read every hole in the view with its sheet position and the origin, and log them with what each step returned.
- Round 2: make one of each table type with three groups and compare them against the reference with Aidan.
- Check every member against the Inventor API reference before trying it (`CLAUDE.md`). Results go in this file.

**Round 1 (2026-11-12): reading the view, run on Aidan's test part and drawing (read-only).**

Test setup: one part of Aidan's own, all holes made with AWB Hole (each `HoleFeature` carries the `AWB_Hole` attribute set): Hole7 (plain, 2 centres), Hole8 (plain, 1), Hole9 (plain, 4), Hole10 (plain, 1), Hole11 counterbore (2), Hole12 countersink (1), Hole13 spotface (1), Hole14 tapped M6x1 blind (3), Hole17 taper tapped Rc 1/8 (1). - **B5, holes and their sheet positions: use the model's hole centres (route 2).** For each `HoleFeature` of the view's part, `HoleCenterPoints` gives the centres in order (each a `SketchPoint`, object type 83896576), and `DrawingView.ModelToSheetSpace(point.Geometry3d)` gives the sheet position. Every centre on VIEW1 landed exactly on the grid it was sketched on (for example Hole7 #1 at 2.5, 2.5 cm from the origin). The centre's index in `HoleCenterPoints` is the `Id`'s index (task 155) with no matching needed.
- **End on or seen from the side (question 16):** the hole's axis against the view direction works. View direction is the camera's `Eye.VectorTo(Target)`, normalised; the axis is the first side face's `Geometry.AxisVector`. On VIEW1 |axis·dir| was 1 for every hole; on VIEW2 it was 0 (5.5e-32), and the centres there collapse onto one line, so VIEW2 must list no holes. A taper tapped hole has no cylinder side face: its side face is a cone (`kConeSurface` 5893), so the axis must also be read from a cone (round 1 printed n/a for Hole17). A tolerance such as |dot| > 0.999 is enough.
- **Route 1, the view's drawing curves, is not usable on its own.** `DrawingView.DrawingCurves` has an optional argument, so late-bound callers must pass it (`DrawingCurves(Missing)`); C# with the interop can omit it. VIEW1 gave 25 circles (`kCircleCurve` 5124): hole edges (`kUnknownEdge`, model geometry an `Edge` whose faces name the hole feature, sometimes with the extrusion) and cosmetic thread circles (`kThreadEdge`, model geometry a `Face` with no feature). The side view VIEW2 also returned 8 `kCircleCurve` curves whose centres sit on the hole lines, so a circle does not mean a hole seen end on. Curves carry no centre index. Route 1 may still be useful later to tell a hidden hole from a visible one (question 6); not tried yet.
- **B8, the ordinate origin:** Aidan dimensioned VIEW1 with Inventor's single **Ordinate** command, not an ordinate dimension set: `OrdinateDimensionSets.Count` was 0 and `OrdinateDimensions` held two single ordinates (one horizontal, one vertical, both value 0, both attached, both with `Intent.PointOnSheet` at the corner, parent view VIEW1). Placing them made Inventor give VIEW1 an origin indicator: `HasOriginIndicator` true, `OriginIndicator.Intent.PointOnSheet` at the same corner, `InUse` and `Attached` true. VIEW2, with no ordinates, has no origin indicator. So the view's `OriginIndicator` is the origin to read for single ordinates, and a view without one has no origin (the stop). Not yet seen: an ordinate dimension set, and whether a set also creates or uses the origin indicator (question 17).
- **B9, title block and border:** `TitleBlock.RangeBox` and `Border.RangeBox` read cleanly on an ANSI sheet (86.36 x 55.88 cm): the title block's range box (65.405, 2.540) to (85.090, 8.890) cm, the border's inner range box (1.270, 2.540) to (85.090, 53.340) cm. `TitleBlock.Position` is an insertion point outside the sheet for this block, so Align should use `RangeBox`. The corner above the title block is therefore (title block max X, title block max Y).
- Enum values met (round 1): `HoleTypeEnum` kDrilledHole 21505 (plain and tapped both report it; `Tapped` and `TapInfo` tell them apart: `HoleTapInfo` 83920384, `TaperedThreadInfo` 83920640), kCounterSinkHole 21506, kCounterBoreHole 21507, kSpotFaceHole 21508; `DrawingViewTypeEnum` kStandardDrawingViewType 10501, kProjectedDrawingViewType 10504; `DimensionTypeEnum` horizontal 60162, vertical 60163; `DrawingEdgeTypeEnum` kUnknownEdge 82695, kThreadEdge 82689.

- **How Inventor's hole table draws symbols (from `HoleTableCell.FormattedText`):** the cell text is in the table's data style (`Note Text (ANSI)`, Tahoma 0.3048 cm, not bold, width scale 1). Each symbol is one character in the AIGDT font, in its own override at the same size: `<StyleOverride Font='AIGDT' FontSize='0.3048'>n</StyleOverride>`. The characters: `n` diameter, `v` counterbore, `w` countersink, `x` depth, `Â` (U+00C2) spotface, drawn as a boxed SF. Round 2's "Â" was this spotface symbol, not a decoding fault. A space in Tahoma follows each seat and depth symbol. Lines are split with `<Br/>`. Values are live `<HoleProperty HolePropertyID='…' Precision='2'>` fields. The degree sign is a plain U+00B0 in Tahoma. Neither Tahoma nor AIGDT has a glyph at the Unicode symbol code points (U+2300, U+2334, U+2335, U+21A7), so round 2's Unicode text was drawn from a fallback font: smaller and thinner than Inventor's symbols.
- **What a custom table cell refuses (probe 3p):** `Cell.Value` is plain text only. Formatted text (`StyleOverride`, `<Br/>`, stacked-text tags, even a hole table cell's own `FormattedText` copied in) is shown as literal tag text. CR LF gives two lines. A merged cell draws its text in the first row of the merge, not centred vertically. A cell has no justification or font member, so a symbol in the AIGDT font cannot be placed in a cell.
- **What worked instead: the cells stay empty and general notes are drawn on top.** The table holds HOLE, XDIM and YDIM as cell values; DESCRIPTION and NOTES are merged per group with empty values. Each description line, and each NOTES `-`, is a `GeneralNotes.AddFitted` note with formatted text in the hole table's data style, centred on its merged cell, so the symbols are exactly Inventor's (same font, size and weight). Each description line is its own note at Inventor's line pitch (1.75 x text height): one note with `<Br/>` and AIGDT overrides spaces its lines about 1.5 times wider, which overflowed the rows. Drawback: the notes are not part of the table. If someone drags the table, the text stays behind, so the add-in must own the table's position, or re-place the notes on Update. The notes carry an attribute set (`AWB_Spike_Overlay`) so they can be found again.
- **Deviations stacked:** a toleranced description is three notes in a row: the size and fit (`Ø6.00 H6`), a two-line note with the deviations left aligned (`+0.008` over `+0.000`), and the termination (`THRU`). It never wraps.
- **Tables:** "Precision Table: VIEW1" (A1, B1–B2, C1: Hole8 P7, the Hole7 dowels H6, Hole19 G6) and "Tap and Clearance Table: VIEW1" (D to K: plain, seated cbore/csink/spotface, tapped, taper tapped). Letters follow spec 04's decided order, and numbers go by Y then X. XDIM and YDIM are in mm from VIEW1's origin indicator, 2 decimals for precision and 1 for tap and clearance. Descriptions carry extra decimals when the value needs them (Ø2.25), as Aidan agreed for the spike. Text styles are copied from the reference hole table (`DataTextStyle`, `ColumnHeaderTextStyle`, `TitleTextStyle` are writable). Column widths are measured with temporary fitted notes, plus one text height of margin each side, and shared by both tables, so both are 11.864 cm wide. Every row is 1.1577 cm, Inventor's own two-line row height, because the precision rows need two lines for the stack. The clearance table's bottom right sits on the title block's top right corner and the precision table sits straight above it.
- **Thread facts:** `HoleTapInfo.TapDrillDiameter` and `TaperedThreadInfo.TapDrillDiameter` are strings already in mm (M6 "5", Rc 1/8 "8"). `TaperedThreadInfo.EngagementLength` is a double in mm (6.5); `EffectiveLength` came back empty for Rc 1/8. `HoleTapInfo.ThreadDepth` is a parameter in cm. Note that AWB's own attribute gives Rc 1/8's drill as 8.4 mm and a 16.8 mm drill depth on a through hole, while Inventor says 8.0 and through; the table uses Inventor's values. To check with task 155.
- **Tags:** each tag is a sketched symbol (`AWB_Spike_HoleTag`, one `<Prompt>` text box in the hole tag's text style) placed with `SketchedSymbols.AddWithLeader(def, [point, centre intent], …)` and `LeaderVisible = false`, so there is no leader and no arrow. The symbol lands centred on its placement point, so the point is set half a tag up and right of the spot just outside the hole's outer circle at 45°. The outer circle is the largest drawn circle at the centre, seat included (G1's countersink, R 0.915 cm). **They follow the view:** moving VIEW1 by (+2, +1) cm moved the tag by exactly (2.0000, 1.0000), and moving it back restored it exactly. Not yet tried: whether they follow a model change.
- **Precision centre mark:** `CentermarkStyle` has no fill or symbol option (only MarkSize, GapDistance, ExtensionLength, OvershootDistance, DefaultRadius), so a distinct centre mark cannot be made through the centre mark API. Instead, a sketched symbol (`AWB_Spike_PrecisionMark`: a circle with quadrants 1 and 3 filled by `SketchFillRegions.Add`) is attached to the hole centre with a one-point `AddWithLeader` (accepted) and the leader hidden. It is scaled to 0.6 x the hole radius, at most 0.2. It shows on A1, B1, B2 and C1.

- **Cell text, what the API allows (probe 5p):** a custom table `Cell` has only `Value` (a string), `Static`, `IsMerged` and `MergedCell`: no `FormattedText`, font or stacked-text member. `CustomTable.OverrideFormat` (`TableFormat`) only sets line colours, line weights and one text style for the whole table. Formatted text is shown as literal tags however it gets in: `CustomTables.Add` Contents, `Rows.Add` Contents and `Cell.Value` all behave the same. What a cell does take: Unicode, and a line feed for a second line (`Ø6.6 THRU` over `⌴Ø11.0 ↧6.5`). The Ø is Tahoma's own; the counterbore and depth signs come from a fallback font, small and thin (the round 2 look Aidan rejected). There is no stack, only two lines. **So the descriptions cannot live in custom table cells as Aidan wants them.**

## Recommendations

Aidan checked every round on his `_spike` copy; round 7 passed on 2026-11-17. What the add-in builds, from the results above:

- **Tables (Aidan: option 1).** Each table is one sketched symbol definition (`AWB_HoleTable_<sheet>_<view>_Precision` and `_Clearance`), placed once on the sheet:
  - Grid lines and text boxes are drawn inside the definition (`SketchedSymbolDefinition.Edit`, `SketchLines.AddByTwoPoints`, `TextBoxes.AddFitted`), with the text styles, one-line row height, line weights and layer of a standard hole table. Read them from the drawing's hole table style, or, as the spike did, from a temporary hole table that is deleted straight away.
  - The insertion point is the table's bottom-right corner (a sketch point with `InsertionPoint = true` at the origin). Align puts the clearance table there on the title block's `RangeBox` top-right corner, with the precision table straight above it.
  - DESCRIPTION and NOTES are merged per group: the row rules stop at DESCRIPTION. A group's rows share its height evenly. That height is the one-line row plus 1.75 x the text height for each extra line, and never less than one line per row.
  - Descriptions use Inventor's own symbols: one AIGDT character per symbol in a `StyleOverride` at the data text height (`n` diameter, `v` counterbore, `w` countersink, `x` depth, U+00C2 spotface). A toleranced hole stacks its deviations natively (`<Stack FractionalTextScale='1.0'>up^lo</Stack>`, `StackedTextPosition = kAlignTextMiddle`). Each extra description line is its own text box at Inventor's line pitch.
  - Update redraws the definition in place: `Edit`, delete its text boxes and lines, draw again, `ExitEdit(true)`. The placed symbol shows the new values at once and drags as one object. A hand edit inside the definition is overwritten by the next Update; edits go through the wizard (Aidan).
- **Reading a view.** Each `HoleFeature`'s `HoleCenterPoints` go through `DrawingView.ModelToSheetSpace` to the sheet. A hole is listed only when its axis (the first cylinder or cone side face's `AxisVector`) is along the view direction (|dot| > 0.999). The origin is the view's `OriginIndicator` (`HasOriginIndicator`, `Intent.PointOnSheet`); a view without one stops the wizard. Tolerances come from the hole read-back, not from text.
- **Hole id (C11).** The feature name plus the centre sketch point's reference key (`GetReferenceKey`, kept as a string through `ReferenceKeyManager.KeyToString`). The centre index is for display only: it shifts when a centre is removed.
- **Where edits live (C10).** Attribute sets survive save, close and reopen. Keep each table's edits and its tags on the table's sketched symbol. Keep the shared state (letter sequence, view link) on the sheet. On the document, `AttributeSets.Add(name, false)` works; `true` fails.
- **Tags.** One sketched symbol definition (`AWB_HoleTag`, one `<Prompt>` text box in the hole tag's text style), placed with `AddWithLeader(def, [point, centre intent])` and `LeaderVisible = false`. Its lower-left corner sits just outside the outermost circle at 45 degrees. Tags follow the view and model changes.
- **Precision marks.** A sketched symbol (`AWB_PrecisionMark`): a circle of radius 1 with the top-right quadrant filled, scaled to the hole radius, and no centre lines of its own.
- **Centre marks (Aidan, round 7).** Every hole gets the same mark: lines continuous through the hole, ending a fixed 2 mm on paper past the outermost visible circle (the seat, else the thread circle, else the hole), whatever its type or size. Precision holes included.
  - One local style, `AWB Centre Mark`, kept in the drawing and created if it is missing: a copy of the standard's centre mark style with `GapDistance` 0.0001 cm (0 is refused), `MarkSize` 0.01, and `OvershootDistance` and `ExtensionLength` 0.2.
  - With extension lines on, the overshoot is what sets the 2 mm.
  - Added with `Centermarks.Add(CreateGeometryIntent(outermost circle), true, false, style)`. The outermost circle is the largest `kCircleCurve` drawing curve centred on the hole, thread edges included.
- **Update keeps letters.** The spike's refresh kept every hole's letter by its id, then redrew XDIM and YDIM; tags and marks follow the model on their own. Renumber is the button that closes gaps.
- **Not settled, not blocking:** which command made VIEW2's ordinates (the API listed no ordinate set); assembly views and hidden holes (questions 6 and 7 above, not met in the test part).
